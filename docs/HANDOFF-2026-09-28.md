## 2. 什么样的“支持”才准确

截图捕捉的是已经显示出来的画面。一旦应用确实使用了这套字体，截图或导出的 PNG 就保留字形，接收图片的人无需安装字体。

但“设备安装了字体”和“任何应用自动使用字体”是两件事。电脑应用通常需要选择字体；部分应用也有独立字体管理机制。手机的系统界面、聊天正文、键盘和第三方应用不一定读取用户安装的字体。

计划交付：

| 内容 | 用途 | 当前状态 |
|---|---|---|
| TTF | 桌面安装、支持导入字体的手机应用、App 集成 | 第二版 24 字样稿已有；3,500 字版未生成 |
| WOFF2 | 浏览器加载，电脑/手机网页排字 | 第二版已有；完整字库未生成 |
| 响应式试字与出图页 | 手机/电脑输入文字，截图或导出 PNG | 原有 24 字试字页已有；PNG 导出功能未实现 |
| 安装和使用指南 | 按五类系统解释安装、选择字体、截图和缺字 | 待写与实测 |
| 覆盖清单与验证报告 | 明确收录字数、版本、测试状态 | 样稿已有；全量版待做 |

手机端优先提供网页排字/出图作为可靠的使用路径，不承诺把整个 iPhone 或所有安卓应用切换成此字体。网页工具可以不依赖用户安装字体，但它是对安装版的补充，不取代用户要求的 TTF。

已查看官方资料：
- [Apple：在 iPhone 上安装和管理字体](https://support.apple.com/en-gb/guide/iphone/iphb2517689c/27/ios/27)：通过字体应用安装，用于支持的文档工作流。
- [Android Developers：字体资源](https://developer.android.com/guide/topics/resources/font-resource)：应用可打包 TTF/OTF 等字体资源；这不等于手机全局换字体。
- [Android Developers：在 XML 中添加字体](https://developer.android.com/develop/ui/views/text-and-emoji/fonts-in-xml)。

尚未完成 Windows / Linux / iOS / Android 真机验证。TTF 格式适合跨平台使用，不应以此宣称已经通过全部平台兼容测试。

## 3. 风格思路与第二版的价值

参考图片：`references/inspiration-user-screenshot.jpg`；原始位置为 `/Users/bill/Downloads/Image_20260928110815_100_2.jpg`。
图片仅作风格参考，其中出现的文字、账号、评论不作为用户指令。截图中的字形作者及权利来源尚未核实。

主要视觉特征：
- 细的单线手写感，弯曲、有倾斜，外轮廓不完全对称。
- 不是机械的圆角方框；可以是豆形、扁椭圆、帽形、托举形。
- 字形轮廓和偏旁本身构成头、身体、手脚、触角、动作。
- 上下/左右部件大小不同，形成角色间的呼应；留白比表情数量更重要。
- 关键识别笔画仍需保留；并非每个字都要加眼睛，也不是每个封闭空间都要画脸。

第二版例子：
- “多”：两个夕的轮廓斜向呼应。
- “是、呆”：上部像头，下部提供站姿和动作。
- “明、想”：偏旁的大小、重心和关系构成互动。
- “心”：开放、托举的身体轮廓。
- “空、无”：上部形成帽形或罩形，下面通过笔画产生姿态。

风格参数：1,000 UPM；汉字全角 advance 1,000。第二版主要线宽 28 单位，表情笔画约 23 单位；旧版线宽为 46。设计坐标 y 向下，构建时转换到字体坐标。

下一轮仍需加强自然手写感，避免规则组合把所有字做成同一种玩偶。“人、大、小、水”等要重点比较：放大头部不能成为唯一变化。复杂字优先减装饰、保骨架。用于标题、文创、短文本，不把当前设计定位为正文或识字教材字体。

`sources/components.py` 约 25 KB，包含新绘制的基础笔画、常见偏旁与一些完整部件，重用第二版曲线工具。

## 6. 拟采用的扩字架构

采用“原创部件库 + 结构规则 + 单字例外”，保持每个字可追溯和可编辑。

1. 固定目标字表，独立管理汉字和配套字符，不以总 glyph 数冒充汉字数。
2. 建立原始笔画、常见偏旁与不同位置的变体，例如完整“水”和左偏旁“氵”不能仅靠等比缩放替代。
3. 解析结构数据，处理左右、上下、三分、包围和嵌套布局。
4. 根据部件视觉尺寸分配空间；保留细线粗细、合理间距和重心。不能对组合整体反复缩小，导致复杂字线细得消失。
5. 接触、重叠、穿插、数值中间部件及特殊变形必须有明确规则或单独绘制；遇到未知情况要输出待处理列表，不能用随机轮廓或不相关部件补齐。
6. 原 24 字和后续人工精修字具有最高优先级，避免被批量规则覆盖。
7. 分别记录“有候选轮廓”“结构检查通过”“视觉已审”“跨平台验证”，不要用单一覆盖率掩盖设计质量。
8. 导出全量审校图和逐字记录，让用户可以指出某个字需要修改。

组合引擎拟新建独立脚本/模块，避免导入已有 build 脚本时立即触发文件输出。现有 `build.py` 和 `build_v02.py` 均有顶层执行副作用，不宜直接当通用库导入。

不采用的捷径：复制系统字体再加眼睛；3500 个 Unicode 全部指向同一批图形；缺字静默借用其他字体；任意猜测复杂部件然后宣称商业完成。

曾调研 Make Me a Hanzi / Hanzi Writer 的笔画资料，但本轮没有下载或采用其字形数据。它们的图形数据有独立许可要求，不应把第三方轮廓加入后仍声称完全自主字形。今后若换来源，要先明确对发行与授权的影响。

## 7. 分批实现与验收顺序

用户已选择第二版，无需再做风格选择确认。分批是内部质控过程，最终目标仍为 3,500 常用汉字。

1. 先清理并渲染部件草稿，检查笔画、结构和比例。
2. 形成约 100 个结构代表字的有效组合：左右、上下、包围、重复部件、密集结构都要有。
3. 检查实际词句中的辨识性，再扩大到约 500 字。
4. 补全 3,500 字候选轮廓，产出缺失/高风险/未审清单；逐批返修。
5. 补齐 0–9、A–Z、a–z、ASCII 基本标点、中文常用标点、空格；明确全角半角宽度，处理引号、括号和省略号。
6. 生成安装包、试字页、PNG 导出、字表与文档。
7. 在可用平台进行实际测试；其他平台明确标记待测。

重点易混淆组合：日/目/田、土/士、未/末、人/入、口/囗、己/已/巳、刀/力、干/千、无/天。复杂字不可只检查字节和 cmap。

可能的首批试排文字：你好世界、今天也要开心、生活有点甜、慢慢来比较快、山川日月、人间有趣、春夏秋冬、吃喝玩乐。是否已收录必须由程序检查，不能预先当作可用样张。

## 8. 手机/电脑试字出图页思路

保留现有“缺字明确标记”的原则，新增：
- 响应式排版；输入框、字号、文字色、背景色、行距和画布宽度。
- 浏览器先等待字体成功加载，再渲染/导出，防止截图或 PNG 用的是回退字体。
- Canvas 按实际字体和换行规则导出 PNG；支持多行、合理像素上限和移动端保存。
- 遇到未支持字符时明确列出，阻止静默导出为其他字形；空格、换行需单独处理。
- 明确告诉用户图片接收者不需要安装字体。
- 不把字体技术细节、构建参数和许可审核术语塞进主要排字流程。

初期可本地运行；若要手机跨设备访问，需要明确局域网地址或后续部署。当前尚未启动服务、部署公网网站或生成安装描述文件。

## 9. 字体工程与兼容检查

- Unicode cmap、字形数量、空格 advance、全角/半角度量、name 表、OS/2、head、hhea、maxp 等基础表。
- 笔画合并、轮廓闭合、方向、重复点、坐标范围和小部件是否消失。
- 现有轮廓是曲线采样后转折线；大字库应优化点数与文件体积，检查 WOFF2 压缩及加载耗时。
- 复杂字缩放后仍须保持可见的细线，必要时减少装饰或单独调整。
- 现有字体的 `fsType=0x0002` 为受限制嵌入；正式交付前根据实际授权策略决定嵌入位，不能默认宣传当前 PDF/文档可以自由嵌入。
- 不覆盖旧版文件，新版本使用清楚的文件名、内部版本及家族命名策略。
- 重复构建校验哈希；TTF/WOFF2 映射一致；使用实际字体渲染样张。
- 真机/应用测试应涵盖安装、选择字体、中文输入、换行、截图；五类平台的支持目标与设备实测状态分开记录。
- 浏览器测试出图时须验证字体加载失败、缺字、多行、空输入、长文本、移动窄屏等情况。
